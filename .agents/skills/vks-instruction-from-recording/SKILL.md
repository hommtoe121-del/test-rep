# Изготовление инструкций из записи ВКС

Используй этот скилл, когда нужно по видеозаписи экрана/созвона (часто `vks.oro.moscow/records/.../*.mp4`) сделать **Markdown-инструкцию со скриншотами** и при необходимости выложить её в **GitHub Wiki** репозитория.

## Результат

- Новая или обновлённая страница Wiki (или файл `.md` в репо, если Wiki не нужна)
- Скриншоты ключевых экранов (особенно **пакетов действий**, HTTP-настроек, правил, выражений)
- Полные кликабельные ссылки в конце статьи
- Факты, сверенные с видео/транскриптом (не додуманные)

## Порядок работы

### 1. Получить видео

1. Скачай `.mp4` по прямой ссылке.
2. Если обычный `curl` зависает после ~16 KiB (типично для крупных файлов с `vks.oro.moscow`), качай **параллельными Range-чанками** по ~16 KiB и склей файл. Проверь `Content-Length` заголовком и итоговый размер.
3. Сохрани оригинал в `/tmp/.../video.mp4`. Проверь длительность через `ffprobe`.

### 2. Извлечь речь и кадры

1. Вытащи аудио: `ffmpeg -i video.mp4 -vn -ac 1 -ar 16000 audio.wav`.
2. Транскрибируй (например `faster-whisper`, язык `ru`). Сохраняй сегменты с таймкодами.
3. Если в транскрипте большие дыры (>60 с), **перетранскрибируй эти диапазоны отдельно** (без агрессивного VAD).
4. Сними обзорные кадры каждые ~20 с и **плотную сетку** вокруг моментов, где по речи упоминаются пакеты/API/настройки.

### 3. Найти экраны пакетов и настроек

Не полагайся только на редкие кадры. Для админских разборов 1Формы:

1. По OCR (`tesseract rus+eng`) отфильтруй кадры с словами вроде: `Пакет`, `HTTP`, `API`, `Редактирование действия`, `job_creation`, `Комментарий`, URL `smart-pack-action`, `folder-access-controller`.
2. Для **каждого названного пакета действий** добудь:
   - скриншот **состава пакета** (список действий),
   - скриншот **конкретного HTTP/Smart-действия** (URL, метод, параметры).
3. Для правил — скрин модалки «Редактирование смарт-правила» (событие, значение, пакет).
4. Для выражений — скрин редактора SMART с текстом выражения.

Если пакет в речи назван, но в видео его не открывали — в статье явно напиши, что виден только триггер/правило, а состав пакета на записи не показан.

### 4. Подготовить скриншоты для Wiki

1. Обрежь правую полосу ВКС (~250–280 px) и панель задач Windows.
2. Сожми до разумного размера (JPEG quality ~78–82, ширина ≤1400 px).
3. Имена файлов — стабильные и говорящие: `15-pack-job-creation.jpg`, `16-http-job-creation.jpg`.
4. Клади в Wiki-репозиторий: `media/<slug-статьи>/...` и ссылайся как `./media/<slug>/file.jpg`.

### 5. Сверить факты перед текстом

Проверь по кадрам/OCR, а не по памяти модели:

| Что проверить | Типичные ошибки |
|---|---|
| URL API | угаданный path вместо реального (`job_creation` ≠ «добавить предложение» в URL) |
| Параметры HTTP | пропущенный `is_project=true/false`, неверные имена полей |
| Триггер | спутать авто-правило (смена ДП/переход) с ручным селектором вроде «Комментарий 13» |
| Категория 1Формы | 65 БЦ / 80 Клиенты / 61 Сотрудники |
| Смысл поля | одно ДП может быть и автотриггером, и ручным переключателем пакетов |

### 6. Написать Markdown-инструкцию

Структура:

1. Заголовок + источник (полная ссылка на ВКС) + список систем
2. Общая схема / таблица сценариев (триггер → пакет → API)
3. Разделы по процессам: назначение → где смотреть → скрин пакета → скрин HTTP → логика → замечания
4. Ручные/исключительные процедуры отдельным разделом
5. Чек-лист поддержки
6. **Ссылки — только полные URL** (wiki DOC, `smart-packs/N`, каждый API endpoint, шара, запись ВКС). Не оставляй обрубки вроде `/spa/administration/...` без хоста.

Стиль: пошагово, по делу, один процесс — один раздел. Не раздувай встречный трёп; сохраняй операционные предупреждения («нельзя просто перетащить папку на шаре»).

### 7. Опубликовать в GitHub Wiki

Wiki — **отдельный git-репозиторий**: `https://github.com/<owner>/<repo>.wiki.git` (ветка обычно `master`).

1. Клонируй wiki с тем же auth, что у `origin` основного репо.
2. Добавь/обнови `.md` (имя файла = slug страницы) и `media/...`.
3. `git commit` + `git push origin master`.
4. Проверь HTTP 200 страницы Wiki и что картинки открываются.

При **редактировании** существующей статьи: пересмотри видео точечно по замечаниям пользователя (недостающие скрины пакетов, битые ссылки, фактические ошибки), не переписывай всё с нуля без нужды.

## Обход ограничений среды

- **videoReview / multimodal video** часто принимает только ≤15 MB и файл вида `recording_demo.mp4`. Сделай сжатое демо (`scale`, низкий fps/crf/bitrate) и при необходимости дополнительно опирайся на кадры + транскрипт — это основной надёжный путь.
- Крупное видео с ВКС: Range-чанки, не один долгий GET.
- Нужны пакеты: `ffmpeg`, `ffprobe`, `tesseract-ocr` (+ `tesseract-ocr-rus`), `faster-whisper` или аналог, `Pillow`.

## Чек-лист готовности

- [ ] Каждый упомянутый пакет действий имеет скрин состава и/или HTTP-действия
- [ ] URL API, параметры и триггеры сверены с кадрами
- [ ] В конце статьи все ссылки полные и рабочие
- [ ] Скриншоты без полосы ВКС, лежат в `media/`, отображаются на Wiki
- [ ] Отдельно помечены факты «сказано устно» vs «видно в UI»

## Чего не делать

- Не выдумывать endpoint’ы и имена пакетов «по смыслу»
- Не подменять скрин правила скрином пакета
- Не публиковать только текст без визуальных якорей для UI-процессов
- Не оставлять относительные/урезанные ссылки в финальном блоке «Ссылки»
